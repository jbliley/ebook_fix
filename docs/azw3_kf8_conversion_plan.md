# AZW3/KF8 Conversion -- Planning Doc

**Status:** Phases 1-3 done. Not yet building end-to-end conversion (that's Phase 4 onward).
**Started:** 2026-09-24, continuing straight from `docs/mobi_conversion_plan.md`'s "Next: AZW3/KF8" section.

## Why this is its own plan doc, not a MOBI7 addendum

The MOBI7 plan doc's original sketch assumed KF8 was "MOBI7 plus a few extra header fields and a different link scheme." Spending a day with the three real sample files (`AZW3-Example.azw3`, `AZW3-Newer.azw3`, `AZW3-Older.azw3`) showed that's wrong: KF8 keeps the same outer container, header, EXTH, and image records, but a book's actual text is not one continuous stream the way MOBI7's is. It's broken into small interleaved pieces ("skeletons" and "fragments") reassembled through a set of custom, sparsely-documented index tables. That's a genuinely different, harder problem than MOBI7's "decompress and find page breaks," closer to reverse-engineering a second file format than extending the first one -- so it gets its own phased plan rather than a short "AZW3/KF8" section tacked onto MOBI7's doc.

Jacob's call (2026-09-24): keep going, but in incremental, independently-checkable phases rather than one long push, specifically to make this more manageable.

## The three samples

- **`AZW3-Example.azw3`** ("Dead Line" by C.J. Box) -- 212 records, pure KF8 (no legacy MOBI7 half), PalmDOC-compressed text, 190 text records, 70 fragments / 127 skeleton pieces / a 2-entry guide-like index / a 68-entry chapter TOC index.
- **`AZW3-Newer.azw3`** ("The Ballad of Songbirds and Snakes") -- 340 records, same shape as Example, larger book, confirmed to have the identical 4-index-pair layout (see "Reference: what's confirmed so far" below).
- **`AZW3-Older.azw3`** (*Frankenstein*) -- 129 records, also `file_version == 8` (a real KF8 header), but its text is **HUFF/CDIC-compressed**, not PalmDOC -- the compression scheme flagged as "written from the spec, no real sample to verify against" in `mobi_conversion_plan.md`. Also has an EXTH 121 ("KF8 boundary") record present, which turned out to be a false trail -- see Phase 1.

None of the three are a genuine two-header hybrid (a real MOBI7 header *and* a separate KF8 header in the same file, the case `mobi/reader.py` already has an untested code path for). If Jacob comes across one, that code path finally gets a real sample; until then it stays flagged unverified.

## Phases

Each phase should be independently buildable, testable against the real samples, and reviewable on its own before moving to the next -- that's the whole point of splitting it up this way.

### Phase 1: Fix what the real samples already broke in the existing code (done, 2026-09-24)

Two bugs surfaced just from reading these three files with the *existing* MOBI7 code, before any new KF8-specific code was written:

1. **The "KF8 boundary" (EXTH 121) check had a false-positive.** `AZW3-Older.azw3` has an EXTH 121 record (value 117), which `mobi/reader.py`'s old `has_boundary` check treated as "this is a two-header hybrid file, read the MOBI7 half" from its mere presence. Record 117 is actually this file's *own* HUFF dictionary record, not a second MOBI header -- confirmed by scanning every record in the file for a second `MOBI` tag; there isn't one. The EXTH value looks like stale or misleading metadata from whatever tool produced this file, not a real second header pointer. **Fixed:** `_find_valid_kf8_boundary()` in `reader.py` now requires a genuine MOBI header to actually verify at the record EXTH 121 names before treating a file as hybrid, not just the EXTH record's presence. Covered by three synthetic tests (a stale pointer on a MOBI7-version file, the same stale pointer on a file claiming `file_version=8`, and a real constructed two-header file), since none of the three real samples turned out to be genuine hybrids to test the positive case against.

2. **HUFF/CDIC decompression turned out not to be broken at all -- the length check around it was.** Running the existing `HuffCdicReader` (written from the public spec for MOBI7, never tested against a real file) against `AZW3-Older.azw3` gave a decompressed length 1,090 bytes over what the header declared, which first looked like confirmation of exactly the kind of bug that was expected somewhere in an unverified implementation. It wasn't: a reference tool (a small third-party MOBI-unpacking package, used here only as a one-off test oracle, not a dependency) independently decoded the same file, and the visible text in its output matched this project's decompressed output **character-for-character** up to the point where the reference output ends. The extra 1,090 bytes are the book's own embedded CSS, concatenated right after the main text within the same decompressed stream -- confirmed by reading the file's FDST table directly: flow 0 (the main text) is exactly `header.text_length` bytes, and three more flows immediately follow it totaling exactly 1,090 bytes, matching three CSS stylesheets the reference tool extracted separately. The real bug was in `reader.py` assuming, for every generation, that `header.text_length` describes the *entire* decompressed text-record stream; for KF8 specifically it only describes flow 0, with more content legitimately following in the same stream. **Fixed:** the length check is now generation-aware -- a KF8 file (`file_version >= 8`) decompressing to *more* than `text_length` is treated as normal (that excess is exactly what Phase 2 will split out), not a warning or an error; too little is still treated as a real problem, same as before. This is also good news for Phase 2: the extra bytes being real, well-formed CSS content (not garbage) confirms flow separation there is squarely about *splitting*, not repairing anything.

Both were bugs in already-shipped code, found by pointing it at new real files -- fixed here rather than filed separately, since fixing them was a prerequisite for reading `AZW3-Older.azw3` correctly (as a refused-for-now KF8 file, accurately classified) in any later phase.

### Phase 2: Flow separation (FDST) -- done, 2026-09-25

KF8 splits the decompressed text-record stream into "flows": flow 0 is the main HTML text; later flows hold embedded CSS (and, unconfirmed against a real sample, SVG). New module `mobi/kf8.py`: `read_kf8()` (the KF8 counterpart to `mobi/reader.py`'s `read_mobi()` -- refuses anything that *isn't* `file_version >= 8`, the complementary gate to that function's own refusal), `read_fdst()`, and `split_flows()`. `MobiHeader` gained a `fdst_record` field (confirmed at the same offset, `mobi_offset + 176`, across all three real samples). `read_text_records()` (renamed from a MOBI7-only private helper in `reader.py`) is shared as-is between the two readers -- decompression itself doesn't change for KF8, only what happens to its output next.

**A real surprise, caught by testing against all three samples rather than just one:** `header.text_length` is not reliable for telling flow 0 apart from the rest of the stream. In `AZW3-Older.azw3` it happens to equal flow 0's own length (which is what made the Phase 1 investigation look like a clean confirmation at the time); in `AZW3-Example.azw3` and `AZW3-Newer.azw3` it's the *total* decompressed length across every flow instead -- two different KF8-generating tools apparently populate this field differently. Relying on it to validate or warn about flow 0's boundary would have meant a spurious warning on two of the three real samples. Fixed by not using it for that at all: `split_flows()` instead checks FDST's own internal consistency (every flow's range is contiguous with the next, and the last one's end matches the decompressed stream's actual length exactly) and refuses cleanly if that doesn't hold, which is a stronger signal than a header field with inconsistent meaning across files anyway.

**Verified:** flow 0's boundary lands exactly where the real content ends and CSS begins on all three samples, confirmed by eye (each cuts cleanly at a closing tag immediately followed by `@page {`, `.bold {`, or similar). `AZW3-Older.azw3`'s flow 0 ends with the book's own actual final line ("...lost in darkness and distance."), matching *Frankenstein*'s real ending. Five synthetic tests cover: a plain MOBI7 file correctly refused by `read_kf8()` (wrong reader for it), a `file_version=8` file with no FDST record at all cleanly refused rather than guessed at, a correct multi-flow split, and two malformed-FDST cases (a gap between flows, flows not covering the whole decompressed stream) both refused rather than silently mishandled. A single-flow book (no embedded CSS at all) also confirmed to work, since none of the three real samples exercise that case.

**Known gap:** flow 0's own content hasn't been touched yet -- it's still the raw interleaved skeleton+fragment stream from here, not usable HTML on its own. That's Phases 3-4.

### Phase 3: Skeleton and fragment indices -- done, 2026-09-26

`indx.py`'s generic INDX/TAGX/entry decoder (built for MOBI7's NCX) turned out to be exactly the right engine for these tables too, tag-numbering scheme included -- confirmed by literally reconstructing pages from all three real samples and checking the result reads correctly, and cross-checked against a reference tool (the same kind of one-off test oracle used for HUFF/CDIC in Phase 1, not a dependency). It's now factored out as `read_indx_records()`, a domain-neutral walk (INDX header + TAGX, entries, CTOC labels) that `read_ncx_entries()` (MOBI7) and the three new KF8 readers below both call, each applying its own tag-number interpretation on top.

**The Sept 24 sketch above had the two main tables' identities backwards.** It guessed the 127-entry table (no CTOC labels, decimal-string entry ids) was "skeleton" and the 70-entry `SKELnnnnnnnnnn`-keyed one was "fragment, referencing which skeleton each fragment belongs to." It's the other way around: the `SKELnnnnnnnnnn`-keyed table (70 entries in the Example file) *is* the skeleton table -- those are the skeletons' own sequential names, not references to skeletons from elsewhere -- and the 127-entry table is the fragment table, whose entry id (the decimal string, e.g. `"0000000494"`) is literally `int(text)`: the fragment's own insert position, a byte offset into flow 0. New module content, in `mobi/kf8.py` (kept alongside `read_kf8()`/`read_fdst()`/`split_flows()` rather than split out, since Phase 2 already put "flow 0 isn't one document yet" work here):

- `read_skeleton_table()`: tag 1 is the number of fragments (from the fragment table, taken in table order) that splice into this skeleton; tag 6 is two values, `(start, length)` -- the byte range of this skeleton's own template within flow 0, template and insertion point included.
- `read_fragment_table()`: tag 2 is an offset into this table's own CTOC, giving the fragment's "aid" XPath selector text (e.g. `P-//*[@aid='0']`) -- kept as `FragmentEntry.aid` but not needed for reassembly itself; tag 3 and tag 4 are a file number and sequence number (not needed for reassembly either); tag 6 is two values, `(start, length)`, but only `length` matters -- `start` duplicates a position already implied by where the fragment sits (immediately after its skeleton's own template) and a reference tool's own reassembly code doesn't read it.
- `read_guide_table()`: tag 1 is an offset into this table's own CTOC giving the human-readable title (`"Copyright Page"`, `"Table of Contents"`); tag 6 is an index into the *fragment* table, not a skeleton/part number as an earlier guess here might have suggested -- confirmed by a comment in the reference tool's own source ("fileno is actually a reference into fragtbl"), and cross-checked by resolving each guide entry's fragment to the page it lands on and confirming it's a sensible one (a copyright page, a table of contents). Optional: `AZW3-Older.azw3` has no guide index at all, and reading one is treated as a warning, not a hard error, unlike skeleton and fragment (which every sample has, and without which flow 0 can't be turned into pages at all).
- `reassemble_flow0()`: walks the skeleton table in order; for each one, slices its own `[start, start+length)` template out of flow 0, then -- for exactly `fragment_count` fragments, taken next in the fragment table's own order -- slices `length` bytes immediately following the current position as that fragment's content and splices it into the template at `fragment.insert_position` (made skeleton-relative), advancing past both the skeleton's template and each fragment's content as it goes. Produces one complete page (`Kf8Book.pages[i]`) per skeleton entry.

**Verified**, on all three real samples: every reassembled page parses as strict XML (`recover=False`); the concatenated visible text of every page matches a reference tool's own output character-for-character (confirmed after normalizing HTML entity encoding, which the two tools happen to spell differently but decode to the same text); reassembly is deterministic (running it twice on the same file gives identical results, as it must -- there's no ordering ambiguity in the algorithm); every guide entry resolves, through the fragment table, to a real page whose content matches its title (the "Copyright Page" guide entry's fragment really does land inside the page that has the book's copyright text, and likewise for "Table of Contents"); and every byte of flow 0 is accounted for exactly once across every skeleton's template range and every fragment's content range combined (no gaps, no overlaps, and the ranges' total covers flow 0 exactly) -- so the "known gap" flagged for Phase 4 below is genuinely just about turning already-correct content into named files, not about anything left unaccounted for.

**Known gap, carried to Phase 4:** `reassemble_flow0()`'s pages are correct content but not yet standalone files -- they have no `<?xml?>`/`<!DOCTYPE>` header of their own beyond what's already in the first page, aren't individually named, and their internal `kindle:pos:fid:...` / `kindle:embed:...` links still point at the KF8 addressing scheme rather than real hrefs. That's Phases 4 and 6.

### Phase 4: Page reassembly into real files

Phase 3's `reassemble_flow0()` already does the byte-splicing, and already confirmed the global byte-accounting this phase would otherwise need to check (every byte of flow 0 covered exactly once, no gaps or overlaps). What's actually left: giving each page its own well-formed standalone document (its own `<?xml?>` declaration, matching how `mobi/markup.py` and `mobi/epub_out.py` already finish a MOBI7 page) and a real output filename per page (`part0000.xhtml`-style, reusing the fragment table's file-number field where it's actually populated, falling back to sequential numbering otherwise since not every sample populates it meaningfully -- see Phase 3's note that the field isn't needed for reassembly itself).

### Phase 5: Real structure -- guide and table of contents

Two more labeled indices exist alongside skeleton/fragment (confirmed present in all three samples, each with human-readable CTOC labels: one small one that looks like guide-style landmarks -- "Copyright Page", "Table of Contents" -- and a larger one that looks like the book's real chapter-by-chapter TOC -- "Title Page", "Dedication", chapter names). Unlike MOBI7, KF8 books already carry a real, structurally-grounded table of contents here, so this phase should produce a proper nested TOC without any of MOBI7's heuristic-detection uncertainty -- genuinely easier than the MOBI7 equivalent once the index-reading mechanics from Phase 3 are solid.

### Phase 6: Links and images

Resolve `kindle:pos:fid:...:off:...` (internal links), `kindle:embed:...` (images), and `kindle:flow:...` (stylesheets) references within the reassembled pages to real hrefs in the finished EPUB. Images and cover handling reuse MOBI7's existing machinery (same EXTH fields, same record layout) -- confirmed unchanged from MOBI7 by inspection, not yet exercised end-to-end on a KF8 file.

### Phase 7: Assembly, CLI/GUI wiring, full verification

Wire into `ebook_fix.epub_builder` (the shared assembler MOBI and FB2 already use), extend the `convert` CLI command and GUI upload flow to stop refusing `file_version >= 8` files, and run the same battery of checks the MOBI7 and FB2 converters got: strict-XML validity, every link/image/TOC entry resolving, `repair` making only sensible changes and converging to zero on a second pass, full example sweep with no regressions.

### Phase 8 (stretch, only if a sample turns up): fonts, embedded SVG, genuine two-header hybrids

Not blocking a working converter. Flagged as unverified/deferred rather than built speculatively, matching how HUFF/CDIC was originally handled for MOBI7.

## Reference: what's confirmed so far (from exploration, not yet implemented)

Kept here so a future session doesn't have to re-derive it from the raw bytes again.

- **KF8 header fields**, confirmed by cross-referencing against real magic-tagged records rather than assumed from memory: `first_image_record` (the same MOBI7 field, same offset) correctly locates the first image in `AZW3-Example.azw3` (record 203). A block of fields further out in the header (past MOBI7's 232-byte length -- KF8 headers run 264 bytes) holds the FDST record number and count, and separately the record numbers of four INDX-family tables, each empirically confirmed by cross-checking against real `INDX`-tagged records rather than trusted from memorized offsets.
- **Four INDX-family tables per book** (confirmed present, in this order, in both `AZW3-Example.azw3` and `AZW3-Newer.azw3`; `AZW3-Older.azw3` has only three, no guide): the **fragment** table (127 entries in the Example file, no CTOC labels of its own besides "aid" selector text, entry id is a decimal string that's literally the fragment's insert position), the **skeleton** table (70 entries, `SKELnnnnnnnnnn`-keyed, its own sequential names), a small **guide** table with plain-English CTOC labels like "Copyright Page" / "Table of Contents" (2 entries, optional -- absent on `AZW3-Older.azw3`), and a larger one with real chapter-title CTOC labels (68 entries -- the book's real chapter-by-chapter TOC, `MobiHeader.ncx_index_record`, same field MOBI7's NCX uses; reading it is Phase 5's job, not done yet). The header field offsets for the first three (relative to `mobi_offset`, confirmed by brute-force scanning for the record numbers already found by tag-sniffing, and identical across all three real samples): fragment index at +232, skeleton index at +236, guide index at +244 (`0xFFFFFFFF` when absent). Tag-level semantics for fragment/skeleton/guide are now pinned down -- see Phase 3 above; the chapter-TOC table's tags aren't yet (Phase 5).
- **Flow 0 is not simply a sequence of complete pages.** Tried treating each complete `<html>...</html>` span found by direct text search as one output page (70 such spans found in `AZW3-Example.azw3`, matching the fragment index's entry count almost too neatly) -- ruled out by checking that the spans only account for about 4.5% of flow 0's bytes. The real chapter content lives in the much larger gaps between those spans, which is exactly the content the skeleton/fragment system exists to reassemble. No shortcut around Phases 3-4.
- **`AZW3-Older.azw3` is not a real two-header hybrid**, despite carrying an EXTH 121 record that would normally suggest one, and its HUFF/CDIC-compressed text decompresses correctly (verified byte-for-byte against a reference tool) -- both confirmed and fixed in Phase 1.
- **The decompressed text-record stream holds more than just the main text for a KF8 file.** Whatever follows flow 0 (the main HTML) in the same decompressed stream is later flows (CSS, and presumably SVG/fonts for a book that has them) rather than a decompression error. The FDST table (Phase 2, done) gives the exact byte ranges, and is the only reliable source for where flow 0 ends -- `header.text_length` is not: it means flow 0's own length in one real sample and the *total* decompressed length across every flow in the other two.
